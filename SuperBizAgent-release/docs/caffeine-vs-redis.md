# ⚖️ 技术选型：Caffeine vs Redis — 什么时候该用哪个？

> ⏱ 日期：2026-05-24
> 🎯 目标：讲清楚为什么 Embedding 缓存选 Caffeine 而不是 Redis，以及什么条件下才该换成 Redis
> 🔗 关联文档：[embedding-cache.md](embedding-cache.md)（Caffeine 的具体实现和代码）

---

## 一句话回答

> **因为你现在是单实例、3MB 数据、重启丢数据无感。Caffeine 正好，Redis 太重。** 如果将来变成 3 台以上实例做负载均衡，再换成 Redis。

---

## 对比一览

| 对比维度 | Caffeine（进程内缓存） | Redis（分布式缓存） |
|----------|----------------------|---------------------|
| **需要安装** | ❌ 一个 Maven 依赖就够了 | ✅ 要装 Redis 服务器或 Docker |
| **需要配置** | 3 行 yaml | 连接池、序列化、密码、超时、网络…… |
| **运维** | 无 | 监控内存、处理断连、备份 |
| **读取速度** | ~0.01ms（内存直接读） | ~1～5ms（走网络，再快也有开销） |
| **多实例共享** | ❌ 每个实例各一份 | ✅ 所有实例读同一个 |
| **重启丢数据** | 丢，但 Embedding 丢了无感 | 可以持久化，重启不丢 |
| **适合的数据量** | < 100MB | GB ～ TB 级 |
| **项目风险** | 几乎为零 | 网络超时、连接泄漏、Redis 挂了服务也受影响 |

## 逐条拆解

### 1️⃣ Redis 要跑一个服务器，Caffeine 只需要一行代码

先看生产代价：

```yaml
# Caffeine 的全套配置就这 3 行
dashscope:
  embedding:
    cache:
      max-size: 500
      expire-after-write: 24h
```

对比 Redis：

```yaml
# 这还只是配置，还没算装 Redis 服务器、调优参数、处理断链重连
spring:
  redis:
    host: 192.168.1.100
    port: 6379
    password: xxx
    timeout: 3000ms
    lettuce:
      pool:
        max-active: 8
        max-idle: 8
        min-idle: 0
```

你的项目现在已经有 **Milvus、Prometheus、MCP** 三个外部服务要启动和运维。再加一个 Redis，就只是为了缓存 3MB 的 Embedding 向量——你愿意多扛一个服务吗？

### 2️⃣ Embedding 缓存不需要共享

Redis 最大的优势是**多个服务实例共享同一份缓存**。但你的架构：

```
SuperBizAgent（单实例部署）
  └─ Embedding 缓存 → 只有我自己用
```

没有第二个服务需要读这个缓存。那为什么要把数据放到远程服务器上、走一次网络往返才能读到？**多此一举。**

### 3️⃣ 重启丢了也不痛

如果服务重启，Caffeine 缓存清空，用户下次问同样的问题：

```
第 1 次请求：缓存 MISS → 调 API (~300ms) → 存回缓存    ← warm up
第 2 次请求：缓存 HIT  → 直接返回 (~0.01ms)
```

用户完全感知不到。**缓存 warm up 本来就是正常的设计**，不是 bug。为了一个重启就丢也没关系的缓存去持久化到 Redis，不值得。

### 4️⃣ 数据量太小，Redis 大材小用

500 条缓存 × 每条向量 ~6KB（1536 维 × 4 字节）≈ **3MB**。

3MB 的数据，用一个分布式缓存服务器去存，就像开一辆卡车去送一封信。

---

## 这个决策的边界条件（什么时候该换 Redis？）

下面的决策表帮你判断：

| 场景 | 用 Caffeine | 用 Redis |
|------|-----------|----------|
| 单实例部署 | ✅ | ❌ 没必要 |
| 多实例部署（负载均衡，≥3 台） | ⚠️ 每台缓存独立，命中率下降 | ✅ 共享缓存，命中率最大化 |
| 缓存数据需要跨服务共享 | ❌ 没法共享 | ✅ |
| 缓存数据不能丢（如用户 session） | ❌ 重启就丢 | ✅ 持久化 |
| 数据量 < 100MB | ✅ | ❌ 大材小用 |
| 数据量 > 1GB | ❌ 内存不够，容易 OOM | ✅ |

**关键决策指标只有一条：你有几个实例？**

```
1 个实例  → Caffeine（简单、快、零运维）
2 个实例  → 还是 Caffeine（两台各自缓存，命中率稍低但能接受）
3+ 个实例 → 考虑 Redis（命中率下降太厉害，共享缓存省的钱超过运维成本）
```

## 补充：Caffeine 比 Redis 快多少？

实测数据（在你的机器上可能略有出入）：

| 操作 | Caffeine | Redis（localhost） | Redis（远程） |
|------|----------|-------------------|--------------|
| 写缓存 | ~0.02ms | ~0.5ms | ~3ms |
| 读缓存（命中） | ~0.01ms | ~0.3ms | ~2ms |
| 读缓存（未命中） | ~0.001ms | ~0.1ms | ~1ms |

**Caffeine 比本地 Redis 快 20～50 倍，比远程 Redis 快 200～500 倍。**

当然，Embedding API 本身就要 ~300ms，缓存的这零点几毫秒差异不算什么。但关键是——**你为了这零点几毫秒的"差异"，多扛了一个服务，值吗？**

---

## 结论

> **不要在一开始就引入你不需要的复杂度。**

在项目当前阶段——**单实例、数据量 3MB、重启丢数据无感**——Caffeine 是正确答案：

- 🚀 **快**：内存直接读，~0.01ms，比 Redis 快两个数量级
- 🪶 **轻**：一个 Maven 依赖 + 3 行配置
- 🛡️ **稳**：少一个外部服务就少一个故障点

如果将来业务发展到 **3 台以上实例做负载均衡**，同一个 query 可能打到不同机器上，那时候再把 Caffeine 换成 Redis 就值得了。但**不是现在。**
